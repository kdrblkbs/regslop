Running regslop as an internal service

regslop keeps regulatory documentation in line with the code it describes. Today it is a command-line tool: you write a regslop_config.toml, provide tokens and run it yourself. This page proposes hosting it as an internal service. Teams register their software product once, then start a run from the browser and review the result in git.

What regslop is

Regulated software needs documents such as a test concept, architecture documentation or a backup and recovery concept. Writing them is tedious, and keeping them current as the code changes is worse. regslop is an agent that reads the source code and brings those documents up to date.

Evidence only

Every statement is grounded in the repositories: a file, a test, a CI job, a configuration value. It never invents test results, approvals, dates or people.

Placeholders instead of guesses

When something can't be determined from the code, such as an approver or a document ID, regslop inserts a numbered [[TODO-NNN: …]] placeholder where the value belongs.

A status report per run

Open tasks with the likely owner, findings that need human judgment, every change with its evidence, and the chapters it confirmed without changes.

How regslop works today

One run reviews one document. Everything the CLI needs is in a single configuration file.

  1. 1

    Load regslop_config.toml

    [git]: provider (GitHub or GitLab, including self-managed), token, in_repos (one or more source repositories) and out_repo (the documentation repository). [bedrock]: model, endpoint, limits, and the system and task prompts.

  2. 2

    Prepare a sandbox and clone

    A fresh regslop_sandbox/ directory with in/ for the source repositories and out/ for the documentation repository. The git token is passed as an HTTPS-only header scoped to the repository's origin, so it is never written to disk and never shown to the model.

  3. 3

    Agent loop on Amazon Bedrock

    The model gets three tools: list_files, read_file and write_file. They are confined to the sandbox, refuse .git and won't follow symlinks out of it. The loop runs until the model ends its turn, or stops after max_iterations.

  4. 4

    Result

    The updated chapters and REGULATORY_STATUS_REPORT.md are written to out/, following the templates and the conventions in the documentation repository's README.

Not implemented in regslop yet: pushing the result as a branch, opening a merge request, and reading tokens from the environment. The mock assumes pushing a branch works, and keeps a place for the merge request link.

What the service should offer

The service is a thin layer around the same engine. It stores what is in regslop_config.toml today, manages the credentials, runs regslop on demand and keeps the results visible.

A

Register a software product

A product is one to many source repositories plus one documentation repository, which is exactly the [git] section of the config. The documents to maintain (test concept, architecture, …) are selected per product. The remaining config values have sensible defaults and can be changed per product.

B

Onboarding

If the documentation repository doesn't exist yet, the service offers to create it. It pushes a README with the conventions regslop relies on, plus a template with instruction comments for every chapter of the selected documents.

C

Trigger a run

One click per document starts regslop with the product's configuration. Progress is visible live: clone, each iteration, every tool call, and token usage.

D

Results with links to git

The status report is rendered in the browser, together with the diff and the open TODOs. Every result links to its branch, its commit and the report file in git. Once regslop opens merge requests, the merge request is linked there too.

From config file to product settings

regslop_config.tomlIn the service
git.providerProduct → Git provider
git.in_reposProduct → source repositories (one or more)
git.out_repoProduct → documentation repository; created by onboarding if it doesn't exist
git.tokenGit connection per host and group, managed centrally rather than per product
bedrock.model, base_url, max_iterations, max_tokens, client_timeout_minsProduct → model settings, prefilled with the service defaults
bedrock.system_promptService default (today's prompt from the example config), can be overridden per product
bedrock.task_promptOne per document, generated from a template and editable. {{date}} is filled in when the run starts
bedrock.tokenService level, never per product

Each document of a product can be exported as a regslop_config.toml that the CLI accepts unchanged, which is useful for debugging a run locally.

Why a service and not just the CLI

No setup per team

No local Rust toolchain or CI job to wire up, and no TOML to maintain. Registering a product takes a few minutes.

Credentials in one place

Git and Bedrock tokens are managed centrally instead of sitting in config files on laptops.

Visible to QA and regulatory affairs

The people who own the documents can read status reports and open TODOs without cloning repositories.

One prompt, maintained once

Improvements to the system prompt and task templates reach every product immediately.

Not in a first version

  • Automatic triggers, such as on push to the default branch or nightly.
  • Filling in placeholders from the browser. For now they are edited in git, during review.
  • Custom document types beyond the four templates.

Open questions

Where do runs execute?

One container per run on the internal cluster, or jobs on the existing CI runners. The sandbox is a plain directory today, so a container adds a second layer of isolation.

Which Bedrock account and region pay for the runs?

A run costs roughly one to three dollars with the current default model. A shared account with per-product cost reporting is probably enough.

Who can register products and start runs?

Mapping SSO groups to git groups would let anyone with access to the repositories use them in the service, and nobody else.

How long are run logs kept?

Timelines contain file paths and model messages, and reports contain references to code. They should probably follow the retention of the documentation repository itself.
